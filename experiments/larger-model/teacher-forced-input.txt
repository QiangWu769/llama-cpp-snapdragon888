Mobile inference experiments should separate storage layout, numerical correctness, and hardware activity. A model may store compressed weights while computing matrix products with floating point arithmetic. Data conversion can require substantial vector work before the matrix engine receives its inputs. A larger model therefore does not automatically keep every compute engine busy.

A controlled comparison uses the same prompt, sequence count, context length, thread configuration, and precision policy. The reference must represent the same effective weights. Independently compressing two layouts can change the values that share a scale. Reconstructing actual dequantized weights avoids that ambiguity. Fixed token histories also prevent an early sampling difference from changing all later inputs.

Every measurement should identify the observed interval and the hardware clock. Sampling can miss short operations, and a percentage can use a denominator that excludes sleep. Raw event rates, complete interval coverage, and an independently calibrated control are more informative than an unexplained utilization label. Engine activity cannot reveal whether every lane performs useful work.

Memory pressure includes more than the live buffers counted by an application. A kernel can retain mappings after a library releases its references. An allocation can fail even when system memory remains available. Preserving the kernel error and the precise operation that failed helps distinguish arithmetic failures from transport failures. A bounded staging pool can limit distinct mappings, but copying weights introduces another cost.

Independent sequences contribute real rows to a matrix batch. A single stream contributes one row even when the hardware executes a larger physical tile. Padding should not be counted as useful tokens. Aggregate token throughput and the latency experienced by one sequence answer different questions. Reporting both prevents a batch speedup from being mistaken for faster interactive generation.
